# Antigravity Context & Rules

- **High-Stakes Environment**: This project is an important project that has a lot of users live in production. 
- **Thorough Verification**: Agy (Antigravity) must double-check work before implementing changes. This means deeply scanning through all relevant files and being completely certain before making any modifications.
- **Long-Term Thinking**: Do not make bad long-term decisions simply to be "risk averse". Always prioritize what is best for the application's long-term health and architecture.
- **Build Verification**: Always run `dotnet build` to verify the project builds successfully after making changes. **CRITICAL:** In your response to the user, the VERY LAST LINE must explicitly state whether the solution was built successfully with an emoji to start and end it (e.g. "✅ **Solution Built Successfully** ✅").
- **Querying Production Data**: To query the production database securely without making random bash scripts, use a dedicated .NET console script (like `scratch/dbtest`). Crucially, remember to compile and run the `.dll` directly (e.g. `ASPNETCORE_ENVIRONMENT=Development dotnet scratch/dbtest/bin/Debug/net10.0/dbtest.dll`) rather than using `dotnet run`, as direct SDK runner processes may be killed/blocked by the OS security constraints. Use the connection string `BettingAppDB_Dev` found in `dotnet user-secrets list`.
- **CRITICAL: Editing Production Data**: Reading PROD data is fine, but if the user ever asks to EDIT, UPDATE, or DELETE any production data, you MUST triple-check with the user first. Before making any destructive or modifying queries, you MUST explicitly provide the user with the exact data that will be changed and the exact script that will run, and wait for their explicit confirmation before executing.
- **Fast and easy way to check bet IDs**: When the user needs to quickly lookup or verify a Bet ID (in DEV or PROD), do not overcomplicate it. Use `dotnet user-secrets list` to retrieve the `BettingAppDB_Dev` or `BettingAppDB_Prod` connection string. Then, write a very short, direct C# console script in `scratch/dbcheck` that queries the `Bets` table by `Id` using `Npgsql`, and compile and run it (remembering to run the `.dll` directly, e.g. `dotnet scratch/dbcheck/bin/Debug/net10.0/dbcheck.dll`). Dump the bet details to console.
- **Do not delete scratch tests**: Never delete tests or scripts placed in the `scratch/` directory (like dbcheck or oddstest) after you are done with them. Keep them around to avoid having to rewrite them next time. The `scratch/` folder is excluded from the main project build, so keeping them will not break the main compilation.
- **Fast API Testing and Data Exploration**: For quick debugging, data exploration, or testing third-party APIs (like OddsPapi) without the overhead of compiling a C# project, use inline Python 3 scripts via the terminal (e.g. `python3 -c "import urllib.request, json; ..."`). This allows for rapid iteration and inspecting raw API JSON responses.
